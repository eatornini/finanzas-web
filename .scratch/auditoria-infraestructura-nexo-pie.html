Auditoría de infraestructura — NEXO PIE

Qué es hoy el código, qué necesita para correr en producción, y qué tipo de hosting económico con dominio propio le alcanza.

Repositorio finanzas-web Fecha 28 sep. 2026 Tamaño del proyecto ~11 MB (sin node_modules ni .git)
Corrección de punto de partida

El pliego de preguntas asume un stack Next.js + React + Prisma + TypeScript + Tailwind. Ese stack no existe en este repositorio. Revisé package.json, todo src/, supabase/ y el árbol completo: no hay next, react, prisma ni tailwind en ninguna dependencia ni import.

Lo que hay es mucho más simple de alojar: un sitio estático en JavaScript vanilla (ES modules, sin build) que habla directo con Supabase (Postgres + Auth + Storage + 1 Edge Function). Este informe está construido 100% sobre ese código real, no sobre el stack asumido. Es una buena noticia para el objetivo de hosting económico: casi no hay infraestructura de servidor que pagar.

02Arquitectura de la aplicación

Es un sitio 100% estático (SPA sin build) que consume un backend administrado externo (BaaS). No es SSR, no es SSG, no es "híbrida" — no hay servidor de aplicación que renderice nada. El navegador carga index.html, ese archivo importa src/main.js como módulo ES, y desde ahí todo el enrutado (src/ui/router.js) y el estado corren en el cliente.

Elemento buscadoResultado
app/, pages/, app/api/No existen — no aplica (no es Next.js).
Server actions / route handlersNo existen.
MiddlewareNo existe middleware de servidor. La única "puerta" de acceso es RLS en Postgres + el estado estado='activo' de perfiles.
Componentes que tocan la BDToda la carpeta src/data/*.js llama a supabase-js directo desde el navegador (PostgREST + RPC), protegido por RLS, no por un backend propio.
Generación de informessrc/ui/reportesView.js + src/logic/reportes.js: agregación y gráficos renderizados en el cliente a partir de funciones RPC de Postgres. No genera PDF ni documentos — no hay librería tipo jsPDF.
Procesamiento de archivosEl OCR de comprobantes corre íntegramente en el navegador (WASM + Web Worker). Ningún archivo se procesa en un servidor.
Algo que requiera Node.js en producciónNada. El único cómputo "de servidor" real es una Edge Function de Supabase (Deno) para 3 operaciones administrativas puntuales.

Traducido a la pregunta de hosting: todo lo que hay que alojar es un puñado de archivos estáticos. El backend (Postgres, Auth, Storage, la Edge Function) ya vive en la infraestructura de Supabase y se contrata/dimensiona aparte, con total independencia de dónde se sirvan los archivos estáticos.

03Base de datos

PostgreSQL, administrado por Supabase (no hay motor propio que instalar ni mantener). El frontend nunca abre una conexión SQL directa: habla HTTP contra PostgREST usando la anon key, y toda la autorización real la hace Row Level Security en el propio Postgres.

Tablas propiascategorias, movimientos, perfiles — 3 tablas.
RelacionesSimples: movimientos.categoria_id → categorias.id, y ambas con user_id → auth.users. Nada de tipo muchos-a-muchos.
Migraciones7 archivos SQL secuenciales en supabase/migrations/ (001 a 007), más schema.sql como snapshot completo para proyectos nuevos. Se corren a mano en el SQL Editor de Supabase — no hay Prisma Migrate ni herramienta de migraciones automatizada.
SeedsNo hay script de seed aparte: la función sembrar_categorias_default() crea categorías por defecto vía trigger cuando se registra un usuario nuevo.
Funciones RPC~12 funciones plpgsql/sql (agregaciones, administración, copiar mes, etc.), varias security definer para saltarse RLS de forma controlada.
Tamaño inicial estimadoCon 10–30 cuentas de uso personal (gastos/ingresos), del orden de unos pocos MB. Muy por debajo de cualquier límite de plan económico.
Hallazgo — no es de hosting, es de modelo de datos

El esquema actual modela gastos personales por cuenta de usuario (una persona, sus movimientos, sus categorías). No existe ninguna tabla de estudiantes, casos, profesionales asignados ni nada que represente el dominio de un programa PIE escolar. Si NEXO PIE necesita llevar 500–1000 fichas de estudiantes, este esquema no las soporta hoy — es un rediseño de datos, no un problema de servidor. Vale la pena resolverlo antes de dimensionar hosting, porque cambia completamente el volumen y la forma de los datos.

¿Base de datos en el mismo servidor o administrada aparte? Ya está resuelto: siempre administrada aparte (Supabase). No tiene sentido ni es necesario instalar Postgres en el hosting económico — de hecho la mayoría de los hostings compartidos baratos ni lo ofrecen.

04Archivos y almacenamiento

QuéDónde vive
Fotos de comprobantes (src/data/storage.js)Supabase Storage, bucket privado comprobantes, un folder por usuario, con URLs firmadas de 1 hora. No toca el filesystem del servidor.
Exportación/importación de datos (exportarImportarSeccion.js)Un JSON armado y descargado en el navegador (construirArchivoExportacion). No pasa por ningún servidor ni se guarda ahí.
PDFs / informes / documentosNo se generan. No hay librería de PDF en el proyecto.
Modelo de OCR + WASM (assets/ocr)Archivos estáticos versionados en el repo: 8,7 MB (traineddata + wasm + worker). Se descargan al navegador la primera vez y quedan cacheados por el service worker.
Archivos temporalesNinguno persistente — todo el procesamiento (OCR) es en memoria del navegador.

Consecuencia práctica: el servidor de hosting nunca escribe archivos de usuario. Por eso un filesystem efímero (típico de PaaS baratos) no es un problema acá — no hay nada que dependa de persistir algo en disco del lado del servidor.

05Recursos necesarios

Para el escenario planteado (1 colegio, 500–1000 estudiantes como universo de datos, 10–30 cuentas de profesionales usando el sistema):

CPU del hosting de archivos estáticosIrrelevante — no ejecuta código, solo sirve bytes. Cualquier plan, incluso el más básico, sobra.
RAM del hostingIrrelevante por la misma razón.
Almacenamiento del hosting~15–20 MB alcanza hoy (11 MB de proyecto + margen). Sin PDFs ni uploads de servidor, no crece con el uso.
Ancho de banda del hostingBajo: 10–30 usuarios cargando una PWA que cachea el shell offline. El archivo pesado (8,7 MB de OCR) se descarga una sola vez por dispositivo gracias al service worker.
Usuarios concurrentes que soportaEl hosting estático no es el límite (miles, en la práctica). El límite real está en el plan de Supabase (conexiones de BD, cuota de Auth, ancho de banda de Storage) — con 10–30 usuarios el plan Free ya alcanza cómodo.
¿Necesita CDN?No es obligatorio a esta escala, pero viene gratis si se elige Cloudflare Pages / Netlify / GitHub Pages, que ya sirven todo detrás de CDN sin costo extra.
¿Necesita almacenamiento externo?Ya lo tiene (Supabase Storage). No hace falta contratar nada aparte para archivos.

06Variables de entorno

Sin secretos, solo nombres y dónde vive cada una:

SUPABASE_URL
Frontend — hardcodeada en config.js, pública a propósito.
SUPABASE_ANON_KEY
Frontend — misma lógica, protegida por RLS, no por secreto.
SUPABASE_URL
Edge Function admin — inyectada automáticamente por el runtime de Supabase.
SUPABASE_ANON_KEY
Edge Function admin — ídem.
SUPABASE_SERVICE_ROLE_KEY
Edge Function admin únicamente — nunca en el repo ni en el frontend.

No hay AUTH_SECRET, NEXTAUTH_SECRET ni API keys de terceros: toda la sesión y el JWT los maneja Supabase Auth. El hosting de archivos estáticos no necesita ninguna variable de entorno — no hay build ni proceso que las lea.

08Build y despliegue

# instalación (solo para desarrollo/tests, no para producción) npm install # build — no existe paso de build. Los archivos se sirven tal cual están en el repo. # inicio — no hay proceso que "iniciar"; es servir estático (cualquier servidor web: Nginx, Apache, GitHub Pages, Cloudflare Pages...). # prisma generate / migrate deploy — no aplica. Los cambios de esquema se aplican corriendo el .sql correspondiente en el SQL Editor de Supabase (o `supabase db push` con el CLI). # puerto — el estándar del hosting elegido (80/443). No hay puerto de aplicación que configurar.

¿Docker? No es necesario. ¿Deploy directo desde GitHub? Sí, y de hecho ya funciona así hoy: el README.md documenta el deploy actual a GitHub Pages (rama main, carpeta raíz). El mismo patrón "conectar el repo y listo" funciona igual en Cloudflare Pages o Netlify, con la ventaja de admitir dominio propio con más comodidad.

Procedimiento de deployment propuesto

  1. Elegir el hosting de archivos estáticos (ver sección 10) y conectarlo al repositorio de GitHub.
  2. Configurar el dominio propio (DNS del registrador → CNAME/A del hosting) y esperar el certificado HTTPS automático.
  3. Actualizar config.js si cambia el proyecto de Supabase, y en Supabase → Authentication → URL Configuration, apuntar Site URL / Redirect URLs al dominio nuevo (hoy apunta a GitHub Pages).
  4. Aplicar supabase/schema.sql (proyecto nuevo) o las migraciones pendientes (proyecto existente) en el SQL Editor.
  5. Desplegar la Edge Function admin (supabase functions deploy admin).
  6. Cada push a main despliega solo; no hay pipeline de build que mantener.

09Seguridad (técnica, no legal)

Base sólida: RLS activo y correcto en las 3 tablas propias, operaciones de administrador protegidas por security definer + chequeo explícito de rol, y la service_role key correctamente aislada en la Edge Function (nunca en el repo). Riesgos a corregir antes de producción, de mayor a menor:

SeveridadHallazgo
MediaLa Edge Function admin responde CORS con Access-Control-Allow-Origin: "*" — conviene restringirlo al dominio de producción.
MediaEl bucket comprobantes no tiene file_size_limit ni lista de MIME permitidos configurada del lado de Supabase Storage — el filtro por extensión hoy vive solo en el cliente (storage.js), que se puede saltar.
Media@supabase/supabase-js se importa en vivo desde esm.sh en cada carga de la app, en vez de estar vendoreado como ya se hizo con Tesseract.js. Es dependencia de disponibilidad y de cadena de suministro en cada visita.
AltaEl email transaccional por defecto de Supabase tiene un límite de ~2–4 correos/hora. Con 10–30 cuentas de staff registrándose o pidiendo reset de contraseña en un lapso corto (arranque del colegio), se satura. El propio README ya lo marca como pendiente: hace falta SMTP propio antes de ir a producción real.
AltaNo hay backups automatizados en el proceso actual. El plan Free de Supabase no incluye point-in-time recovery. Con datos reales de personas (y potencialmente de estudiantes), esto no debería quedar en "fuera de alcance".
BajaNo hay rate limiting propio — se depende de los límites de plataforma de Supabase, razonable a esta escala pero vale tenerlo presente si el uso crece.

10Tipo de hosting que necesita

Ninguna de las categorías A–E calza perfecto porque todas asumen que hay algo corriendo del lado del servidor. Acá no hay nada — es más simple que cualquiera de ellas. La clasificación correcta es:

Categoría real

A. Hosting estático / compartido tradicional — y le sobra. Ya corre hoy en GitHub Pages, el hosting estático más básico que existe. Cualquier plan de hosting compartido barato que sirva HTML/CSS/JS (que es prácticamente todos) cumple. VPS (C), PaaS tipo Render/Railway (D) o Vercel (E) son sobre-ingeniería para este proyecto: están pensadas para correr procesos de servidor (Node, contenedores, funciones), y acá no hay ninguno que correr.

La única condición real a exigirle al hosting: que sirva archivos estáticos por HTTPS y permita apuntar un dominio propio. Nada más. La complejidad de "backend" (BD, Auth, Storage) ya está resuelta y facturada aparte por Supabase, independiente de esta decisión.

Recomendación de infraestructura

Para NEXO PIE

No busques hosting Node.js, VPS ni PaaS — es más de lo que el proyecto necesita hoy. Lo que hay que contratar es hosting de archivos estáticos con dominio propio y HTTPS, punto. Concretamente:

  • Hosting: Cloudflare Pages (o Netlify) conectado al repo de GitHub, con el dominio propio apuntado ahí. Gratis en el volumen de tráfico esperado, y no exige aprender nada nuevo sobre el deploy actual.
  • Especificación mínima a exigir si en cambio se prefiere un hosting compartido tradicional: que sirva archivos estáticos, soporte dominio propio con certificado SSL/Let's Encrypt automático, y permita subir archivos por Git o SFTP. Nada de CPU/RAM mínima real — hasta el plan más chico de cualquier proveedor cumple.
  • Base de datos/Auth/Storage: se mantienen en Supabase, decisión independiente del hosting. Empezar en el plan Free; pasar a Pro (~$25/mes) apenas el colegio empiece a usarlo de verdad, sobre todo por backups y para que el proyecto no se pause.
  • Antes de ir a producción con datos reales de un colegio: resolver el punto de la sección 3 (el esquema es de finanzas personales, no de un programa PIE con estudiantes) y los dos hallazgos de severidad alta de la sección 9 (SMTP propio y backups). Ninguno de los dos es un problema de hosting — son de datos y de configuración de Supabase.
